# База данных (v0.6.1, схема v9)

SQLite через sqflite, файл `smart_fridge.db` в приватной папке приложения.
v1 (Шаг 1) — **продукты** и **профиль пользователя**; v2 (Шаг 2) —
**сохранённые планы меню**: `meal_plans`, `planned_meals`, `shopping_items`;
v3 (Шаг 3.1) — **кэш автопоиска штрих-кодов**: `barcode_cache`;
v4 (v0.5.0) — колонки: `user_profile.diets` (список диет), 
`shopping_items.missing_grams` (учёт граммов), `meal_plans.filter_report`
(диагностика «почему рецепты исключены»); v5 (v0.5.4) — нелюбимые продукты
(`user_profile.dislikes`, `planned_meals.minor_dislikes`); v6 (v0.5.5) —
цена продукта (`products.price`, `price_updated_at`, `price_source`).
Встроенная база рецептов (541 блюдо) в SQLite не дублируется — она лежит
активом `assets/data/recipes.json`, а в планы пишутся JSON-снимки рецептов,
поэтому сохранённые планы не ломаются при обновлении базы.

## Кэш автопоиска (v3, Шаг 3.1)

### `barcode_cache` — найденные в открытой базе товары

Автопоиск нового штрих-кода идёт в открытую базу Open Food Facts;
найденное сохраняется здесь, поэтому повторное сканирование того же
товара работает офлайн. Отрицательные результаты не кэшируются —
база постоянно пополняется, стоит пробовать снова.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `code` | TEXT PK | сам штрих-код (EAN-8/13, UPC, Code 128) |
| `name` | TEXT NOT NULL | название товара (с брендом, если он «потребительский») |
| `category_key` | TEXT | категория приложения, определённая по тегам OFF (null — не удалось) |
| `source` | TEXT NOT NULL, default `openfoodfacts` | источник записи |
| `fetched_at` | TEXT NOT NULL | UTC-метка запроса |

## Таблицы планов меню (v2, Шаг 2)

### `meal_plans` — заголовок плана

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | TEXT PK | Стабильный id вида `p<неделя старта>-<seed>`: одинаковый запрос → одинаковый id (повторная генерация с тем же seed заменяет черновик) |
| `created_at` | TEXT | Момент генерации (ISO-8601) |
| `start_date` | TEXT | Первый день плана, `yyyy-MM-dd` |
| `days_count` | INTEGER | Горизонт (обычно 7) |
| `kcal_target` | INTEGER | Целевой суточный калораж из профиля на момент генерации |
| `seed` | INTEGER | Зерно детерминизма: тот же seed + данные = тот же план |
| `source` | TEXT | `rule_based` (движок рецептов) / `local_llm` (Шаг 3+) |
| `warnings` | TEXT | JSON-массив предупреждений («срочно: продукт не вошёл в план», отклонения калоража дня > 15%) |
| `filter_report` | TEXT | JSON {counts, examples}: диагностика «почему рецепты исключены» — причина → количество и до 3 примеров (v4, у старых планов NULL) |

### `planned_meals` — приёмы пищи плана

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | INTEGER PK | — |
| `plan_id` | TEXT FK → meal_plans **ON DELETE CASCADE** | Владелец |
| `day_index` | INTEGER | День плана (0–6) |
| `slot` | TEXT | breakfast / snack / lunch / dinner |
| `slot_order` | INTEGER | Порядок в слоте (при 5–6 приёмах бывает два-три перекуса) |
| `recipe_id` | TEXT | Идентификатор в `assets/data/recipes.json` (для аналитики) |
| `recipe_json` | TEXT | **Полный JSON-снимок рецепта** — план самодостаточен и переживает обновления встроенной базы |
| `kcal` | REAL | Калорийность порции (денормализовано для быстрых сумм дня) |
| `uses_expiring` | TEXT | JSON-массив названий срочных продуктов (≤ 2 дней), закрываемых приёмом |
| `coverage` | REAL | Доля некладовых ингредиентов, найденных в холодильнике (0..1) |

Индекс `idx_planned_meals_plan (plan_id, day_index, slot_order)` — чтение
плана одним запросом в порядке отображения.

### `shopping_items` — список покупок плана

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | INTEGER PK | — |
| `plan_id` | TEXT FK → meal_plans **ON DELETE CASCADE** | Владелец |
| `ing_key` | TEXT | Канонический ключ IngredientMatcher |
| `name` | TEXT | Отображаемое название ингредиента |
| `checked` | INTEGER | 0/1 — чекбокс «куплено» (экран покупок Шага 3) |
| `missing_grams` | INTEGER | Сколько докупить в граммах: суммарная потребность рецептов недели минус масса в холодильнике (v4; NULL — счётная позиция/старый план) |

Список покупок — это некладовые ингредиенты выбранных рецептов,
которых нет в холодильнике или не хватает по массе; соль/масло/специи
(pantry) не попадают. Масса позиции известна для граммов/миллилитров
(1 мл ≈ 1 г); штуки и упаковки считаются достаточными — вес штуки без
таблицы соответствий определить нельзя.

### Индексы

| Индекс | Зачем |
| --- | --- |
| `idx_products_barcode` UNIQUE **частичный** (`WHERE barcode IS NOT NULL`) | Один и тот же штрих-код не добавится дважды; ручные продукты без кода не ограничены |
| `idx_products_status_expiry (status, expiry_date)` | Главный запрос холодильника: активные по возрастанию срока |
| `idx_products_category (category_key)` | Группировка, сезонность, статистика |

Профиль ровно один: строка с `id = 1` (CHECK в схеме), upsert-семантика.

| Поле | Тип | Default | Назначение |
| --- | --- | --- | --- |
| `daily_calories` | INTEGER | 2000 | Суточный калораж, ккал |

| `allergies` | TEXT | '[]' | JSON-массив ключей аллергенов: milk, eggs, fish, shellfish, nuts, peanuts, soy, wheat, sesame |

## Договорённости о датах

- `expiry_date` хранится как `yyyy-MM-dd`: **лексикографический порядок
  строк совпадает с хронологическим**, поэтому все сравнения сроков в SQL —
  честные строковые сравнения без разбора дат.
- Логика свежести (`core/freshness.dart`) сравнивает календарные дни:
  `истекает` = 0 ≤ дней ≤ 2 (порог синхронизирован с пушами ТЗ «за 1–2 дня»).
- Время суток учитывается только в `added_at`.

## Политика миграций

- `onCreate` создаёт схему текущей версии; `onUpgrade` накатывает версии
  последовательно (if-цепочка `oldVersion < N`), каждая миграция —
  идемпотентный DDL-батч только с добавлением таблиц/индексов.
- v1 — Шаг 1 ТЗ (products, user_profile). v2 — Шаг 2 ТЗ (планы меню);
  v3 — Шаг 3.1 (кэш штрих-кодов); v4 — v0.5.0 (диеты-списком, граммы
  покупок, отчёт фильтра; единичная диета из `diet` переносится в `diets`);
  v5 — v0.5.4 (нелюбимые продукты); v6 — v0.5.5 (цена Пятёрочки в products);
  v7 — v0.5.9 (лечебные столы Певзнера: `user_profile.medical_diets`);
  v8 — v0.5.11 (индекс цен Mercadona из SharedPreferences в SQLite:
  `mercadona_index`, SCAN-6);
  v9 — v0.6.1 (валюта цены продукта: `products.currency`, UI-6) —
  Данные при миграциях не трогаются —
  поведение закреплено тестом `test/data/migration_test.dart`.
- Обратная совместимость: неизвестные ключи словарей не роняют чтение.

## Тестирование схемы

Хост-тесты без эмулятора: `sqflite_common_ffi` даёт настоящую SQLite.
`AppDatabase.open(absolutePath: ...)` принимает путь — тесты работают
во временных каталогах (`test/data/`, `test/ai/`, `test/state/`).
Покрытие (v0.2.0, всего 129 тестов): roundtrip моделей, уникальность
штрих-кодов, границы сроков, статусы, upsert профиля, миграция 1→2
с сохранением данных, каскадное удаление планов, roundtrip снимков
рецептов, чекбоксы покупок, валидация всей базы рецептов
(541 рецепт: уникальность, границы КБЖУ, согласованность флагов диет).
