# База данных — Шаг 1 (v0.1.0, схема v1)

SQLite через sqflite, файл `smart_fridge.db` в приватной папке приложения.
Схема описывает ровно Шаг 1 ТЗ: **продукты** и **профиль пользователя**.
Таблицы планера (`recipes`, `meal_plan`, `shopping_list`) добавляются
миграцией v2 на Шаге 2 — после подтверждения архитектуры заказчиком.

## Таблица `products`

| Поле | Тип | Обязательное | Назначение |
| --- | --- | --- | --- |
| `id` | INTEGER PK AUTOINCREMENT | да | Идентификатор |
| `name` | TEXT | да | Название (непустое, trim на записи) |
| `category_key` | TEXT | да | Стабильный ключ категории (см. словарь ниже) |
| `barcode` | TEXT | нет | EAN-13/EAN-8/UPC; NULL при ручном вводе |
| `quantity` | REAL | да (default 1.0) | Количество |
| `unit_key` | TEXT | да (default 'pcs') | Ключ единицы: pcs/g/kg/ml/l/pack |
| `expiry_date` | TEXT | да | Дата истечения `yyyy-MM-dd` (без времени) |
| `added_at` | TEXT | да | Момент добавления, полный ISO-8601 |
| `kcal_per_100` … `carbs_per_100` | REAL | нет | БЖУК на 100 г/мл — из Open Food Facts; нужно планеру для сверки с профилем |
| `notes` | TEXT | нет | Заметка пользователя |
| `status` | TEXT | да (default 'active') | active / consumed / discarded |

### Индексы

| Индекс | Зачем |
| --- | --- |
| `idx_products_barcode` UNIQUE **частичный** (`WHERE barcode IS NOT NULL`) | Один и тот же штрих-код не добавится дважды; ручные продукты без кода не ограничены |
| `idx_products_status_expiry (status, expiry_date)` | Главный запрос холодильника: активные по возрастанию срока |
| `idx_products_category (category_key)` | Группировка, сезонность, статистика |

| dairy | Молочное | 7 дн. |
| meat | Мясо | 3 дн. |
| fish | Рыба | 2 дн. |
| vegetables | Овощи | 7 дн. |
| fruits | Фрукты | 7 дн. |
| bakery | Хлеб/выпечка | 3 дн. |

## Таблица `user_profile`

Профиль ровно один: строка с `id = 1` (CHECK в схеме), upsert-семантика.

| Поле | Тип | Default | Назначение |
| --- | --- | --- | --- |
| `daily_calories` | INTEGER | 2000 | Суточный калораж, ккал |
| `protein_g` / `fat_g` / `carbs_g` | INTEGER | 150 / 67 / 200 | БЖУ в сутки; дефолт — формула 30/30/40 от 2000 ккал (`UserProfile.defaultsForCalories`) |
| `diet` | TEXT | 'none' | Ключ диеты: none / vegetarian / vegan / lent (пост) / pescatarian / low_carb |
| `allergies` | TEXT | '[]' | JSON-массив ключей аллергенов: milk, eggs, fish, shellfish, nuts, peanuts, soy, wheat, sesame |
| `meals_per_day` | INTEGER | 3 | Приёмов пищи в день (2–6, контроль в UI онбординга) |
| `region_name` | TEXT | NULL | Регион для сезонности (название) |
| `latitude` / `longitude` | REAL | NULL | Координаты; из широты выводится климатическая зона для сезонности |
| `onboarded` | INTEGER | 0 | Пройден ли онбординг |
| `created_at` / `updated_at` | TEXT | — | Аудит изменений |

## Договорённости о датах

- `expiry_date` хранится как `yyyy-MM-dd`: **лексикографический порядок
  строк совпадает с хронологическим**, поэтому все сравнения сроков в SQL —
  честные строковые сравнения без разбора дат.
- Логика свежести (`core/freshness.dart`) сравнивает календарные дни:
  `истекает` = 0 ≤ дней ≤ 2 (порог синхронизирован с пушами ТЗ «за 1–2 дня»).
- Время суток учитывается только в `added_at`.

## Политика миграций

- `onCreate` создаёт схему текущей версии; `onUpgrade` накатывает версии
  последовательно (по case), каждая миграция — идемпотентный DDL-батч.
- v1 (эта) — Шаг 1 ТЗ. v2 (Шаг 2) — recipes/meal_plan/shopping_list.
- Обратная совместимость: неизвестные ключи словарей не роняют чтение.

## Тестирование схемы

Хост-тесты без эмулятора: `sqflite_common_ffi` даёт настоящую SQLite.
`AppDatabase.open(absolutePath: ...)` принимает путь — тесты работают
во временных каталогах (`test/data/`), 24 теста: roundtrip полей,
уникальность штрих-кодов, границы сроков, статусы, upsert профиля.
