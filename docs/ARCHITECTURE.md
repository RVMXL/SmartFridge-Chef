# Архитектура — Умный Холодильник & Шеф-Планер

Документ соответствует состоянию **v0.2.0 (Шаги 1–2)** и описывает целевую
архитектуру всех трёх шагов ТЗ. Разработка поэтапная: Шаг 1 (данные) и
Шаг 2 (AI-слой) готовы, Шаг 3 (экраны, сканер, пуши) — следующий.

## Решаемые боли

1. **Трекинг сроков годности** — продукты вводятся сканированием штрих-кода
   или чека; каждому назначается дата истечения; за 1–2 дня приходит пуш.
2. **Персональное меню на неделю** — «Суперпланер» одной кнопкой собирает
   меню на 7 дней из содержимого холодильника, профиля питания и сезонности
   региона, с рецептами и списком недостающих ингредиентов.

## Принципы

| Принцип | Как реализован |
| --- | --- |
| Offline-first | База и генерация меню — целиком на устройстве; сеть только по действию пользователя (Open Food Facts) |
| Приватность | Без аналитики, серверов, аккаунтов; `allowBackup=false`; профиль не покидает телефон |
| Локальный AI | On-device модель без API-ключей + детерминированный офлайн-фолбэк |
| Поэтапность | Каждый шаг ТЗ = версия схемы БД = релиз; ничего «недоделанного» в main |

## Слой данных (Шаги 1–2, готов)

- **SQLite через sqflite**, схема v2: `products`, `user_profile` (Шаг 1)
  + `meal_plans`, `planned_meals`, `shopping_items` (Шаг 2)
  (подробно — [DATABASE.md](DATABASE.md)).
- DAO изолируют SQL от домена; все запросы — параметризованные.
- Даты хранения: `expiry_date` — только дата `yyyy-MM-dd` (лексикографический
  порядок строк совпадает с хронологическим), `added_at` — полный ISO-8601.
- Свежесть (core/freshness): порог 2 дня — синхронизирован с пушами ТЗ.

## AI-слой (Шаг 2, реализован)

### Как устроено (3 уровня провайдеров, один JSON-контракт)

Основной путь — **детерминированный движок рецептов**, работает офлайн
«из коробки» за миллисекунды. LLM и системные нейронки — опциональные
надстройки над ним, а не замена: безопасность (аллергии/диета) и
структура плана гарантированы слоем фильтров и контрактом, а не моделью.

```text
PlanRequest (холодильник + профиль + seed)
      │
      ▼
MealPlanner (интерфейс, lib/ai/planner.dart)
      ├── RuleBasedPlanner   ← по умолчанию И фолбэк (v0.2.0 ✓)
      ├── LocalLlmPlanner    ← каркас; Gemma/MediaPipe подключается на Шаге 3;
      │                         статус notInstalled → прозрачный фолбэк
      └── PlatformAiPlanner  ← интерфейс-заготовка под Android AICore /
                                Apple Foundation Models (Шаг 3+)
```

### Встроенная база рецептов (assets/data/recipes.json)

541 блюдо RU+EN, собрано `scripts/gen_recipes.py` (в корне внешнего
проекта): комбинаторика проверенных шаблонов (белок × способ × гарнир,
базы × добавки) + таблица пищевой ценности ~95 продуктов. Для каждого
рецепта: КБЖУ на порцию, аллергены, флаги диет, минуты, порции,
ингредиенты с граммами (кладовые помечены pantry) и шаги приготовления.
Целостность базы закреплена тестами (уникальность, границы КБЖУ,
согласованность флагов).

### Приоритеты генерации (в порядке убывания жёсткости)

1. **Безопасность**: аллергии и диета — жёсткий фильтр рецептов целиком
   (не скоринг: рецепт с аллергеном не выбирается никогда).
2. **Сроки**: срочные продукты (≤ 2 дней) получают наибольший бонус —
   попадают в первые дни; приём помечается «срочно: …».
3. **БЖУ/калораж**: калорийность слота стремится к цели профиля
   (распределение по mealsPerDay 2–6); отклонение дня > 15% — варнинг.
4. **Покрытие холодильника**: IngredientMatcher (нормализация + ~140
   RU/EN синонимов) считает долю закрываемых ингредиентов.
5. **Разнообразие**: анти-повторы рецепта (−90), «семьи» блюда (−60) и
   гарнира (−30) по нарастающей.
6. **Джиттер**: детерминированный Random(seed) — воспроизводимость и
   вариативность по кнопке «Другая неделя».

### Выход — GeneratedPlan (соответствует JSON-контракту ниже)

План содержит дни (слоты с рецептом-снимком, «срочные» продукты,
покрытие), итоги КБЖУ дня, список покупок (недостающие некладовые
ингредиенты) и предупреждения. Контракт текстом (для LLM-провайдера
Шага 3 — тот же формат, невалидный ответ → фолбэк на движок):

```json
{
  "days": [
    {
      "date": "2026-10-26",
      "meals": [
        {
          "slot": "breakfast",
          "recipe": {
            "title": "Овсянка с бананом и молоком",
            "ingredients": [
              { "name": "овсяные хлопья", "amount": "60 г", "from_fridge": true }
            ],
            "steps": ["Вскипятить молоко…", "Всыпать хлопья…"],
            "kcal": 380, "protein_g": 14, "fat_g": 9, "carbs_g": 62,
            "uses_expiring": ["молоко"]
          }
        }
      ],
      "totals": { "kcal": 2050, "protein_g": 105, "fat_g": 70, "carbs_g": 240 }
    }
  ],
  "shopping_list": [
    { "name": "куриное филе", "reason": "нужно по плану, нет в холодильнике" }
  ],
  "warnings": ["Рыба истекает 2026-10-27 — поставлена в обед вторника"]
}
```

### Провайдеры и их статус

| Провайдер | Что это | Статус |
| --- | --- | --- |
| `RuleBasedPlanner` | Движок по встроенной базе: фильтры + скоринг, без сети и модели | v0.2.0 — готов, по умолчанию и фолбэк |
| `LocalLlmPlanner` | Gemma 2B/3n IT через MediaPipe (flutter_gemma); модель ~1.5 ГБ скачивается опционально; ответ валидируется контрактом, брак → фолбэк | Каркас готов; подключение — Шаг 3 |
| `PlatformAiPlanner` | Android AICore / Apple Foundation Models — зрелых Flutter-биндингов пока нет, контракт уже позволяет подключить | Интерфейс-заготовка |
| Сайты с рецептами | Отклонено: ломает offline-first (парсинг, права, лимиты, приватность). Возможен опциональный открытый источник (TheMealDB) как отдельный RecipeSource на Шаге 3+ | Не реализуется в v0.2.0 |

### Хранение планов (схема v2)

`meal_plans` + `planned_meals` + `shopping_items` (подробно —
[DATABASE.md](DATABASE.md)). Рецепты хранятся полными JSON-снимками:
план самодостаточен и переживает обновления встроенной базы. Миграция
1→2 только добавляет таблицы, данные Шага 1 не трогаются.

## Экраны и интеграции (Шаг 3)

| Экран | Логика |
| --- | --- |
| «Мой холодильник» | Карточки продуктов с цветом свежести (зелёный/жёлтый/красный), сортировка по сроку, свайпы «съел / выбросил» (статусы), FAB: скан / ручной ввод |
| Сканер | `mobile_scanner` → штрих-код → `getByBarcode` (есть в базе?) → Open Food Facts (название, категория, БЖУ) → подтверждение с датой из типового срока категории |
| OCR чеков | `google_mlkit_text_recognition` on-device → разбор строк → чек-лист позиций → пользователь отмечает продукты холодильника |
| «Мое меню» | Календарь недели, слоты приёмов по профилю, карточка дня с суммами БЖУ, предупреждения «съесть раньше» |
| Покупки | Недостающие ингредиенты плана, чекбоксы, связь с вводом продуктов |
| Пуши | За 2 и за 1 день (константа `kPushDaysBefore`), планирование при вставке/изменении продукта, пересборка после перезагрузки (boot-восстановление пакета) |

## Локализация и оформление

- RU + EN через `flutter gen-l10n` (`lib/l10n/*.arb`), выбор «системный/ru/en».
- Material 3, seed #2E7D32; светлая/тёмная/системная тема; цвет свежести —
  из ColorScheme (primary/tertiary/error), без хардкода цветов в виджетах.

## Тестирование

- Хост-тесты SQLite через `sqflite_common_ffi` (реальная SQLite, без эмулятора).
- Покрыты: roundtrip моделей, частично-уникальный индекс штрих-кодов,
  граничные условия сроков, статусы, upsert профиля, метка онбординга.
- Шаг 2 добавит тесты планировщика (контракт JSON, фильтры аллергий,
  приоритет сроков), Шаг 3 — виджет-тесты экранов.
