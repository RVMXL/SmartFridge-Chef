## [0.2.0] — 2026-10-24

### Добавлено (Шаг 2: AI-слой — «Суперпланер»)

- **Встроенная база рецептов** `assets/data/recipes.json`: 541 блюдо
  (RU + EN), 108 завтраков, 34 супа, 331 основное блюдо, 34 салата,
  гарниры, перекусы, десерты. КБЖУ на порцию, аллергены, флаги диет
  (vegetarian/vegan/gluten_free/low_carb), время готовки, шаги
  приготовления. База собирается скриптом `scripts/gen_recipes.py`
  (комбинаторика проверенных шаблонов + таблица пищевой ценности),
  валидируется тестами.
- **RuleBasedPlanner** — детерминированный движок генерации меню,
  работает офлайн «из коробки», без сети и без модели:
  - жёсткие фильтры безопасности: аллергии и диета исключают рецепты
    целиком, независимо от любого скоринга;
  - приоритет сроков: продукты с истекающим сроком (≤ 2 дней) получают
    наибольший бонус и попадают в первые дни плана, приём помечается
    «срочно: …»;
  - попадание в целевую калорийность слота (распределение по
    mealsPerDay: 2–6 приёмов, доли завтрак/обед/ужин/перекусы);
  - разнообразие: анти-повторы того же рецепта, «семьи» блюда
    (главный ингредиент) и гарнира;
  - список покупок (недостающие ингредиенты, без кладовых) и
    предупреждения (срочные продукты вне плана, отклонения калоража);
  - детерминизм: seed → воспроизводимый план, новый seed → новая неделя.
- **IngredientMatcher** — сопоставление продуктов холодильника с
  ингредиентами рецептов: нормализация (регистр/ё/пунктуация) +
  словарь из ~140 синонимов RU и EN («куриное филе» → chicken_breast);
  непознанные продукты не роняют генерацию, а попадают в предупреждения.
- **Архитектура провайдеров AI** (интерфейс `MealPlanner`):
  RuleBasedPlanner — по умолчанию и фолбэк; `LocalLlmPlanner` — каркас
  локальной LLM (Gemma/MediaPipe, подключение на Шаге 3) с прозрачным
  фолбэком на движок рецептов; интерфейс-заготовка `PlatformAiPlanner`
  под Android AICore / Apple Foundation Models. Качество и безопасность
  гарантированы слоем фильтров, а не моделью.
- **Схема БД v2 + миграция 1→2**: таблицы `meal_plans`, `planned_meals`
  (рецепты хранятся полными JSON-снимками — планы самодостаточны),
  `shopping_items` (чекбоксы покупок). Данные Шага 1 при миграции
  сохраняются — закреплено тестом.
- **PlanDao** и **PlanController**: генерация → сохранение → история →
  открытие → удаление, отметки «куплено»; контроллер уже подключён
  в `main.dart` (экран планера — Шаг 3).
- 129 тестов (было 24): матчер, калораж, целостность всей базы рецептов,
  интеграционные сценарии планера (аллергии/диеты/сроки/детерминизм),
  DAO планов, миграция схемы, PlanController.

### Приватность

- Вся генерация меню — локально; сеть по-прежнему не используется.

## [0.1.0] — 2026-10-24

### Добавлено (Шаг 1: архитектура + слой данных)

- Каркас Flutter-приложения (Material 3, нижняя навигация
  «Холодильник / Меню / Настройки»), светлая и тёмная темы
  с переключателем «системная/светлая/тёмная».
- Локализация RU + EN через `flutter gen-l10n`, переключение языка
  «системный / русский / english» в настройках.
- Локальная база SQLite (v1): таблицы `products` и `user_profile`,
  частично-уникальный индекс штрих-кодов, индексы под главный запрос
  холодильника; политика миграций на последующие шаги (docs/DATABASE.md).
- Модели `Product` (категории с типовыми сроками хранения, БЖУ на 100 г,
  статусы «активен/съеден/выброшен») и `UserProfile` (калораж, БЖУ, диеты,
  аллергии, приёмы пищи, регион для сезонности).
- DAO-слой: выборки «активные по возрастанию срока», «истекает ≤ N дней»,
  «просрочено», сводка-статистика; upsert-профиля с меткой онбординга.
- Логика свежести: зелёный / жёлтый (≤ 2 дней — под пуши ТЗ «за 1–2 дня»)
  / красный, даты сравниваются по календарному дню.
- Общая архитектура системы и контракт AI-планера (docs/ARCHITECTURE.md).
- 24 юнит-теста слоя данных и логики свежести (sqflite_common_ffi, хост).
- CI: `flutter analyze --fatal-infos` + `flutter test --coverage`.

### Решения по приватности

- `android:allowBackup="false"` — данные не уходят в облачные резервные
  копии Google; всё хранится только в приватной папке приложения.
- Сеть не используется на этом этапе; будущие обращения — только
  к открытому API Open Food Facts по действию пользователя.
